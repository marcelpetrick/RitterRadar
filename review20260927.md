# RitterRadar security and reliability review — 2026-09-27

## Assessment

**Fix the browser/API trust boundary, home-label HTML injection, and crawler outbound-request validation first. Do not expose this application to a LAN or the Internet without additional access controls.** The current native instance was started on loopback, which reduces direct remote exposure but does not fix unsafe rendering, malicious upstream content, or missing browser-origin checks.

This review identified **14 actionable findings: 3 high, 7 medium, and 4 low**. Severity describes the impact under the prerequisites stated below, not evidence of an attack. Several items concern privacy, availability, or deployment assurance rather than an independently exploitable vulnerability. No critical vulnerability or evidence of compromise was established. Absence of such evidence is not a guarantee of safety.

The existing suite passes, but isolated security checks reproduced behavior that it does not cover. In particular, **a clean crawl-job failure count is not reliable evidence of successful crawling**: a simulated upstream failure was recorded as a completed job.

At the time of the audit, all 14 findings were open. Remediation was implemented
in the following `v0.1.0` work; verification and deployment limits are recorded
below. Source links in the original findings identify the reviewed baseline and
are retained as historical evidence.

## Scope and limitations

- Reviewed checkout: `8fbada1`, declaring version `0.0.91`. Source references below refer to that revision. The audit commit's version bookkeeping does not represent security remediation.
- Reviewed API routes, application startup/middleware, browser rendering and requests, crawler HTTP transport and adapter boundaries, queue/worker lifecycle, geocoding, database access, startup scripts, dependency declarations, Docker/Compose, CI/release workflows, and existing tests/documentation.
- Inspected local runtime logs and file permissions. Earlier runtime inspection showed one RitterRadar server bound to `127.0.0.1:13370`. No production endpoint was subjected to malicious payloads, flooding, or intrusive probing.
- Reproductions used an isolated in-memory database, FastAPI TestClient, mocked HTTP transport, and Chromium with external browser requests aborted. Neither saved user settings nor production event records were modified by the security probes.
- Browser execution was demonstrated for the tooltip sink. Full DNS-rebinding and cross-origin attacks against the user's Firefox session were **not** attempted. Browser local-network protections may affect delivery; they do not substitute for server validation.
- Dependency checks include installed-version comparison, `pip check`, and a limited review of primary upstream advisories. `pip-audit` and Bandit are not installed. No exhaustive CVE scan, container OS scan, artifact provenance verification, exhaustive git-history secret scan, or host/firewall assessment was completed. These are explicit follow-up tasks, not passing results.

### R01 — Stored home-label HTML injection

**Evidence:** [map.js:117](src/ritterradar/static/js/map.js#L117) passes `label` directly to `bindTooltip`. [filters.js:63](src/ritterradar/static/js/filters.js#L63) loads that label from saved settings, and [settings.py:67](src/ritterradar/api/settings.py#L67) accepts it without restricting HTML. Leaflet's bundled implementation assigns string tooltip content to `innerHTML`. [Leaflet's tooltip documentation](https://leafletjs.com/reference.html#tooltip) describes the string/element content interface.

**Reproduction:** An isolated `PUT /api/settings` stored a synthetic label containing `<img src=x onerror="window.auditXss=1">`; the subsequent settings GET returned it unchanged. Loading the real vendored Leaflet and application map module into an isolated Chromium page, then setting/opening that tooltip, produced `window.auditXss === 1`. The payload only set a test variable.

**Prerequisite/impact:** An attacker must get a malicious label into settings or a geocoding result that becomes a label. The unauthenticated settings endpoint makes this relevant to any client that can reach it; remote delivery to a loopback deployment requires an additional access path. When the tooltip opens, code runs in the application origin and can read settings and invoke its APIs. This does not demonstrate operating-system code execution.

**Fix:** Construct an element, assign the label to `textContent`, and pass that element to Leaflet. Treat geocoder text as untrusted too. Use a fixed allowlist for marker CSS classes rather than interpolating arbitrary `market_type` at [map.js:73](src/ritterradar/static/js/map.js#L73). Current adapters generate known types, so that latter sink is additional hardening, not a separately proven upstream injection.

**Acceptance:** Browser tests cover persisted labels and fresh geocoder labels containing tags, quotes, entities, and event handlers. They must display literally without creating elements or executing script.

### R02 — SSRF through redirects and discovered links

**Evidence:** [http_client.py:64](src/ritterradar/crawler/http_client.py#L64) enables automatic redirects. The domain check at line 73 happens only after the final response is fetched. There is no restriction on private, loopback, link-local, or other non-public destinations. [mittelalterkalender_info.py:99](src/ritterradar/crawler/adapters/mittelalterkalender_info.py#L99) accepts absolute discovered links matching a path pattern and later fetches them at line 197. `_domain_root` takes the last two hostname labels; it is not an effective-TLD parser or an SSRF boundary.

**Reproduction:** A mocked response redirected `https://source.example/events` to `http://127.0.0.1:8123/private`. Both URLs reached the mock transport before `Domain drift` was raised. Separately, `_discover_list_urls` accepted `http://127.0.0.1:8123/mittelaltermarkt/audit-2026-nach-datum.php` as the 2026 list URL. No real internal service was contacted.

**Prerequisite/impact:** A compromised source, malicious redirect, or hostile content in a discovered link can induce server-side GET requests to internal services. Directly discovered internal URLs also pass the current same-request/final-domain comparison. Reachability and internal endpoint behavior determine impact. Response exfiltration, cloud credential theft, and internal code execution were not demonstrated.

**Fix:** Permit only explicitly expected schemes, ports, and source hostnames. Validate every initial and redirect destination before requesting it; bound redirect hops. Reject userinfo and non-public IPv4/IPv6 destinations, including mapped forms. Make validation and the actual connection use the same approved resolution, or enforce destination restrictions in a controlled egress proxy/network policy to avoid DNS rebinding between check and connect. Preserve TLS verification and prevent HTTPS-to-HTTP downgrade. Exact host exceptions are preferable to the current domain-root heuristic. [OWASP's SSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) specifically addresses redirects and destination validation.

**Acceptance:** Mocked initial links, every redirect hop, loopback, private IPv4/IPv6, link-local, DNS answer changes, and disallowed ports are rejected before connection. Required `www`/canonical redirects continue to work.

### R03 — Missing API/browser access boundary

**Evidence:** The routers in [main.py:113](src/ritterradar/main.py#L113) have no authentication dependency. [settings.py:51](src/ritterradar/api/settings.py#L51) returns saved home coordinates/label. [markets.py:121](src/ritterradar/api/markets.py#L121) toggles state with a bodyless POST, and [crawl.py:45](src/ritterradar/api/crawl.py#L45) similarly triggers work. There is no trusted-Host middleware, Origin validation, CSRF token, or Fetch Metadata policy.

**Reproduction:** `GET /api/settings` with `Host: attacker.example` returned 200 without credentials. An isolated POST to `/api/markets/1/hide` with `Origin: http://attacker.example`, `Sec-Fetch-Site: cross-site`, and form content type returned 200 and changed the hidden flag. Cross-origin crawl triggers were also accepted.

**Prerequisite/impact:** A reachable client can read personal settings and change state. On a network-exposed deployment this is direct unauthenticated access. Loopback prevents ordinary direct Internet connections, but other local processes can connect, and browser-delivered requests remain a concern. A hostile Host acceptance is a DNS-rebinding prerequisite, not proof of a complete browser exploit. Missing CORS permission limits cross-origin reads; it does not undo a simple POST's side effects. JSON PUT typically requires preflight and must not be described as automatically exploitable by a simple form.

**Fix:** Keep loopback as the default. Enforce an explicit Host allowlist and exact trusted origins on mutations; handle absent/null origins deliberately for CLI clients. Require a CSRF/custom-request token where appropriate and reject cross-site Fetch Metadata. For LAN/proxy exposure, require real authentication on sensitive reads and writes plus HTTPS. A token embedded in an otherwise publicly readable page is not authentication. Prefer a configured authenticated reverse proxy or a carefully designed local pairing/session mechanism over a hardcoded token. Keep proxy trust limited to known proxy addresses. See [OWASP's CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

**Acceptance:** Unknown Host values and hostile origins fail before database changes or queue admission. Normal Firefox use and explicitly supported CLI calls pass. Exposed-mode startup fails closed without access-control configuration.

### R04 — Unbounded work admission and API cost

**Evidence:** [queue.py:40](src/ritterradar/crawler/queue.py#L40) creates an unbounded queue; [queue.py:123](src/ritterradar/crawler/queue.py#L123) creates another job per enabled source on every trigger, even if that source is already pending/running. Three calls with one synthetic source produced three queued jobs. [settings.py:97](src/ritterradar/api/settings.py#L97) accepts unlimited geocoding requests; the Nominatim lock spaces outbound starts but does not bound the number of waiting requests. [markets.py:69](src/ritterradar/api/markets.py#L69) loads every valid-date market, including large fields, then filters in Python inside an async route. The browser repeats market requests every eight seconds.

**Impact:** A reachable client can grow the queue/database, keep crawlers busy, consume geocoding capacity, or amplify synchronous CPU/database work. R03 increases exposure. This was not load-tested against the live instance.

**Fix:** Allow at most one active job per source, enforced transactionally; bound queue depth and add a trigger cooldown. Apply request/concurrency limits, bounded geocoder admission, maximum query/body lengths, cancellation and appropriate `429`/`503` responses. Bound market responses and avoid blocking the event loop. Preserve date-correction semantics when moving filters into SQL: current-source selection must happen before filters that could resurrect superseded records. Coordinate pagination/result caps with the map and preview.

**Acceptance:** Repeated/concurrent triggers coalesce rather than multiply jobs. Limits recover after work completes; the UI stays responsive under bounded synthetic concurrency; existing date-correction tests still pass.

### R05 — Unbounded upstream resource consumption

**Evidence:** [http_client.py:64](src/ritterradar/crawler/http_client.py#L64) reads responses into memory without a byte limit. HTML/JSON/iCal parsing then runs over those bodies. [mittelaltermarkt_online.py:218](src/ritterradar/crawler/adapters/mittelaltermarkt_online.py#L218) trusts upstream `total_pages` without a local cap, including continued requests for empty pages. There is no overall job deadline. Contrary to the HTTP client's docstring, HTTPX's numeric timeout is not a total wall-clock limit; its read timeout bounds waiting for a chunk. See [HTTPX timeout semantics](https://www.python-httpx.org/advanced/timeouts/).

**Impact:** An upstream can serve huge/decompression-heavy content, trickle data, or advertise a huge page count, consuming memory or occupying workers. This remains relevant even after API authentication.

**Fix:** Stream and cap decoded response bytes as well as wire bytes where feasible; do not trust `Content-Length` alone. Bound pages, records, field lengths, and parser work. Add a total per-request/job deadline and terminate repeated empty/duplicate pages. Reject malformed pagination metadata. Keep the legitimate largest feeds working. Add container memory/CPU/PID limits as secondary protection.

**Acceptance:** Synthetic oversized, compressed, chunked, slow, empty-page, and huge-page-count responses terminate with a bounded resource cost and a clear failure status. No large malicious downloads are needed for the tests.

### R06 — Insufficient validation at API and ingestion boundaries

**Evidence:** [settings.py:33](src/ritterradar/api/settings.py#L33) lacks coordinate ranges, finite-number checks, label length, radius bounds, and coherent month-offset validation. Synthetic latitude/longitude `999`, radius `-1`, and a very large month offset were accepted with 200. [base_adapter.py:22](src/ritterradar/crawler/base_adapter.py#L22) is an unvalidated dataclass. [mittelaltermarkt_online.py:170](src/ritterradar/crawler/adapters/mittelaltermarkt_online.py#L170) trusts JSON coordinate values, and [worker.py:120](src/ritterradar/crawler/worker.py#L120) treats any non-null pair as usable.

**Reproduction:** `_parse_event` accepted a string latitude. Processing a synthetic record with `latitude='invalid'` raised a SQLAlchemy `StatementError`; its job remained `running`.

**Fix:** Validate settings with finite numeric fields, geographic ranges, paired coordinates, length limits, supported radius/month bounds, and explicit partial-update semantics. Introduce a validated ingestion boundary for every adapter: numbers, types, dates, lengths, and URLs. Reject or quarantine malformed individual records with observable counters rather than allowing one record to poison an entire job. Avoid silently converting bad coordinates into trusted locations. Support deliberate clearing of a home location: current `None` checks treat null as no change.

**Acceptance:** Invalid input returns 422 without mutation; valid zero coordinates survive; corrupt upstream records cannot cause persistent 500s, bad map state, or stuck jobs.

### R07 — Misleading success, stuck jobs, and shallow health reporting

**Evidence:** [spectaculum.py:58](src/ritterradar/crawler/adapters/spectaculum.py#L58) catches fetch failures and returns an empty list. Other adapters also swallow some fetch/parse failures. [worker.py:146](src/ritterradar/crawler/worker.py#L146) then marks that job complete and updates source success. Only the adapter call has a `_fail` catch; record processing errors escape to [worker.py:60](src/ritterradar/crawler/worker.py#L60), which logs without setting terminal job state. [queue.py:145](src/ritterradar/crawler/queue.py#L145) counts only the most recent 100 jobs. `/health` is unconditional liveness, not database/crawler readiness.

**Reproduction:** A mocked Spectaculum connection failure resulted in `status='completed', events_discovered=0`. A malformed coordinate resulted in `status='running'` after processing had raised.

**Fix:** Define a common adapter outcome contract that distinguishes legitimate empty results, partial success, and fetch/parse failure. Finalize every job on all exception/cancellation paths. Expose partial/quarantined record counts and source freshness. Separate documented liveness from readiness; label recent-window counters or compute true totals. Do not clear a source error after an unsuccessful/partial crawl.

**Acceptance:** Network, parser, geocoder/storage, unexpected processing, and cancellation failures leave truthful terminal states. Legitimately empty successful feeds remain distinguishable from failures.

### R08 — Personal location data in persistent, broadly readable files

**Evidence:** [filters.js:97](src/ritterradar/static/js/filters.js#L97) puts home coordinates in repeated market-query URLs; [filters.js:135](src/ritterradar/static/js/filters.js#L135) puts address searches in a geocoding GET query. Uvicorn access logs contain these query strings. [nominatim.py:185](src/ritterradar/geocoding/nominatim.py#L185) persists search keys/results without expiration. Observed modes were `0644` for `.env`, `data/ritterradar.db`, and the manually created `/tmp/ritterradar-13370.log`, with `0755` on `data`. Parent directories were traversable in the inspected environment. The temporary log was created for this session, not by a repository logging subsystem.

**Prerequisite/impact:** Other local accounts/processes with filesystem access can read personal search/home data and the configured contact address. There is no evidence of an exposed credential secret. Shared logs, backups, or support attachments create additional disclosure paths. Unlimited logging also consumes disk over time.

**Fix:** Create private data/log directories (`0700`) and files (`0600`) with a restrictive umask; migrate permissions on existing installations, handling container UID ownership correctly. Redact sensitive URL parameters before access logging or omit query strings entirely. Moving geocoding to a validated POST can reduce URL exposure but does not itself solve body logging. Add log rotation/retention, cache expiry, a user-facing clear-home/history operation, and backup handling documentation. Review the existing temporary log as part of deployment cleanup without blindly deleting all user logs.

**Acceptance:** Synthetic addresses/coordinates do not appear in routine logs; fresh and upgraded installs have private files; the privacy-clearing action removes the intended settings/cache data.

### R09 — External privacy flows need controls and clear disclosure

**Evidence:** [base.html:17](src/ritterradar/templates/base.html#L17) automatically loads Google Fonts CSS/fonts. [map.js:11](src/ritterradar/static/js/map.js#L11) loads OpenStreetMap tiles directly from the browser. [nominatim.py:271](src/ritterradar/geocoding/nominatim.py#L271) sends searches to Nominatim; the configured contact address is included in its user agent. README acknowledges tiles/geocoding, but the main UI does not explain these data flows or offer an offline choice.

**Impact:** Font requests disclose browser network/request metadata to an additional party. Tile requests disclose IP and viewed map tiles, from which an area can be inferred; they do not transmit the stored home-label field directly. Nominatim receives the search text from the server and the configured user agent. These are functional external requests, not evidence of malicious exfiltration.

**Fix:** Self-host licensed fonts. Explain geocoding and tile providers near the relevant controls; support configurable providers and an offline/no-external-requests mode where useful. Preserve provider attribution. Do not turn caching/offline mode into bulk tile downloading. Respect the [Nominatim usage policy](https://operations.osmfoundation.org/policies/nominatim/), including its public-service rate requirements; multiple app instances must not multiply the intended rate.

**Acceptance:** Main-page loading contacts no font third party; a browser network test documents allowed destinations and verifies the chosen offline behavior.

### R10 — Unsafe URL schemes accepted for source links

**Evidence:** [mittelaltermarkt_online.py:160](src/ritterradar/crawler/adapters/mittelaltermarkt_online.py#L160) takes the source URL directly from upstream JSON; several HTML adapters use `urljoin`, which is not a scheme allowlist. [detail-panel.js:95](src/ritterradar/static/js/detail-panel.js#L95) HTML-escapes the value but puts it into `href`. A synthetic event containing `javascript:window.auditXss=1` survived parsing unchanged.

**Impact/qualification:** Scheme validation is missing. User activation is needed, and the link currently has `target="_blank" rel="noopener"`; JavaScript execution through this specific link was not demonstrated and must not be counted as another confirmed XSS. Depending on browser handling, non-web schemes may cause unwanted navigation/protocol-handler behavior.

**Fix:** Parse URLs and permit only `http:`/`https:` with a valid host and no embedded credentials, both on ingestion and before rendering. Disable invalid links, including old database records. Preserve legitimate event links on different public domains; display-link rules differ from crawler fetch allowlists. Use `noopener noreferrer` if suppressing the referrer is desired.

**Acceptance:** Mixed-case, whitespace/control-character, `javascript:`, `data:`, `file:`, malformed, and credential-bearing inputs are not actionable links; valid event URLs still work.

### R11 — Missing browser defense-in-depth headers

**Evidence:** [main.py:89](src/ritterradar/main.py#L89) adds only static-cache headers. Isolated responses lacked `Content-Security-Policy`, `X-Frame-Options`, `Referrer-Policy`, and `X-Content-Type-Options`.

**Impact:** There is no application framing restriction or CSP to limit injection consequences. Header absence alone is not evidence of data theft. A permissive framing policy can enable clickjacking where a browser permits the embedding context.

**Fix:** Start with `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`, `nosniff`, a deliberate referrer policy, and a restricted Permissions Policy. Build a working CSP around the actual templates/modules, inline script in the index template, Leaflet styling, tiles, and API documentation assets. Prefer external scripts or nonces instead of `unsafe-inline` for scripts. Test report-only before enforcement where needed. Use HSTS only for a properly configured HTTPS deployment, not as a blanket localhost setting.

**Acceptance:** UI, tiles and supported API documentation work under the enforced policy; an iframe cannot display the app; unexpected scripts are blocked.

### R12 — Dependency/build assurance and version drift

**Evidence:** [pyproject.toml:21](pyproject.toml#L21) pins direct dependencies, but the checkout has no committed transitive lock with artifact hashes. [Dockerfile:10](Dockerfile#L10) uses a versioned image tag rather than a digest; Compose defaults to mutable `latest`. CI does not run a dependency/container vulnerability or secret scan. Installed runtime pins matched the 16 declared direct requirements, and `pip check` passed. Installed package metadata reports RitterRadar `0.0.89` while the reviewed checkout declares `0.0.91`; the imported module points into this checkout, so that is stale metadata, not proof of old application code.

**Impact:** Builds can resolve different transitive versions; provenance and current vulnerability status are not continuously checked. The displayed version is unreliable during incident triage. These observations are an assurance gap, not proof that an installed dependency is exploitable.

**Limited advisory results:** Installed Starlette is `1.3.1`. It is outside the affected ranges of the checked upstream advisories: [GHSA-jp82-jpqv-5vv3](https://github.com/Kludex/starlette/security/advisories/GHSA-jp82-jpqv-5vv3) (fixed in 1.3.0), [GHSA-82w8-qh3p-5jfq](https://github.com/Kludex/starlette/security/advisories/GHSA-82w8-qh3p-5jfq) (fixed in 1.3.1), and [GHSA-wqp7-x3pw-xc5r](https://github.com/Kludex/starlette/security/advisories/GHSA-wqp7-x3pw-xc5r) (fixed in 1.1.0; Windows-specific). This is not an all-packages clearance. Other observed transitive versions include Pydantic 2.13.4, h11 0.16.0, urllib3 2.7.0, and certifi 2026.6.17; no blanket safety claim is made for them.

**Fix:** Produce reviewed locks/hashes for supported Python/platform combinations, pin container base/deployment digests with an update process, inventory vendored JS and native libraries, and add scheduled plus change-triggered dependency/container/secret scans. Audit the resolved production image as well as the development environment. Reinstall editable metadata using the existing pins and verify the displayed version against build/source provenance. Do not blindly upgrade unrelated packages to resolve a metadata mismatch.

**Acceptance:** A clean supported build reproduces its resolved inventory; scanner failure/unavailability is distinct from no findings; published artifacts are traceable to their source revision and reviewed dependency set.

### R13 — Single-instance lifecycle assumptions and unused interval

**Evidence:** [queue.py:104](src/ritterradar/crawler/queue.py#L104) marks every pending/running database job as interrupted when any instance starts. No instance identifier, lease, or singleton lock distinguishes a live sibling process from an orphan. The queues and geocoder rate limiter are process-local. `crawl_interval_hours` is stored/configured but never used by a scheduler; startup and manual trigger are the only enqueue paths found.

**Impact:** Starting two servers with the same database can relabel live jobs, duplicate work and exceed the intended aggregate outbound rate. A long-running instance does not periodically recrawl just because the interval setting is present. Stale event data and misleading job status can result. Earlier runtime checks found one app process, so concurrent corruption is not claimed to have occurred.

**Fix:** For this local application, enforce one owner process per database and fail with a clear message when another owner is active. Alternatively implement job ownership/leases and coordinated rate limiting before supporting multiple workers/processes. Add a real cancellable periodic scheduler that uses the same deduplicating admission path as manual/startup crawling. Correct configuration/documentation and test shutdown/recovery.

**Acceptance:** A second instance cannot interfere with live jobs. Stale jobs recover after a simulated crash, and controlled-clock tests verify periodic scheduling, no overlapping jobs, and clean cancellation.

### R14 — CI privileges and edge quality gating

**Evidence:** [.github/workflows/docker.yml:29](.github/workflows/docker.yml#L29) grants package, OIDC and attestation write permissions to the image job that also performs builds/smoke tests. Publishing steps are correctly conditional on non-PR events, and fork tokens may be restricted by GitHub; this is not a demonstrated credential leak. The master/edge Docker workflow has no dependency on CI success, although the release workflow correctly runs quality checks before calling the container workflow.

**Fix:** Separate read-only PR/build validation from trusted publication with narrow job-level permissions. Require quality success before publishing edge artifacts if they are intended for use. Disable persisted checkout credentials where unneeded, retain SHA-pinned actions, and apply environment/branch rules for releases. Verify those repository settings separately; they are not visible in this checkout.

**Additional quality-gate observation:** The local Sphinx build exited 0 despite autodoc failing to import API modules with `PydanticSchemaGenerationError` about `__pydantic_extra__`. The CI quality workflow does not build documentation. Diagnose the documentation import configuration separately and make relevant warnings fail the documentation gate; an exit code alone currently overstates documentation health.

**Acceptance:** PR builds have no publication capability; failed quality checks prevent edge publication; tag releases still pass their validation/quality/provenance steps.

## Controls that are already useful

- Native binding and documented Compose host-port publication default to loopback. Docker's internal `0.0.0.0` binding is expected and is not itself a public host binding.
- The container runs as UID/GID 10001. Its build-context allowlist excludes `.env` and the database. No Docker socket mount or privileged mode is declared.
- Runtime HTTP clients verify TLS by default. No active `verify=False`, request-driven shell execution, unsafe deserialization, or dynamic SQL string interpolation was found in the reviewed application paths. YAML is loaded with `safe_load` and database queries use SQLModel/SQLAlchemy expressions.
- Event names, program text, tooltip event names, and error messages are generally escaped. The old tracker entry about unsanitized original text does not establish an XSS: the current detail renderer escapes it, and the market API does not include `original_text`.
- `.env` and database files are untracked/ignored; `.env` had no history in the available local refs. A limited pattern scan of 140 tracked files found no private-key, common GitHub-token, AWS-access-key, or embedded URL-credential patterns. This is not a complete secret-history audit.
- Actions use full commit SHAs; release tag/changelog validation, non-PR publication guards, SBOM generation, and provenance steps already exist.
